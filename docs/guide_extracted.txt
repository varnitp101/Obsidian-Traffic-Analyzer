1. What you're building
One system that grows in two stages. Part 1 is the data engineering foundation; Part 2 sits
on top of it and turns it into an MLOps solution.
UK accident CSVs + Open-Meteo API (+ optional OSM)
  -> raw landing zone
  -> Airflow ETL (extract, clean, validate, join)
  -> staging -> cleaned -> PostgreSQL/PostGIS
  -> accident mart + model-ready table
  -> Streamlit dashboard
  -> (Part 2) feature pipeline -> training + MLflow -> model registry
  -> FastAPI in Docker -> Streamlit prediction page
  -> monitoring (drift, latency, false negatives) -> retraining criteria
Build Part 1 so that Part 2 plugs into it without rework. In particular, keep a stable model-
ready table from the start.

PART 1: Data Pipeline
4. Data acquisition
Primary dataset: UK Road Safety Open Data (DfT STATS19), found on data.gov.uk. It ships
as three CSVs per year:
Collisions (accident-level: date, time, lat/long, road type, speed limit, weather, light,
road surface, severity, number of vehicles and casualties)
Vehicles (one row per vehicle: type, manoeuvre, driver age and sex)
Casualties (one row per casualty: age, sex, class, severity)
They link through the collision/accident index column. Column names differ slightly
between years ( accident_index  vs collision_index ), so check the actual headers in
the file you download.
Severity coding: 1 = Fatal, 2 = Serious, 3 = Slight. Map these to readable labels during
cleaning.
Weather source: Open-Meteo historical API. Free, no key needed for non-commercial use.
Optional: OpenStreetMap road context. Skip unless everything else is done.
For the report, record: source name, URL, licence (UK Open Government Licence for DfT
data), the date you downloaded it, and step-by-step access instructions.

5. Ingestion
Write scripts that are repeatable (running twice gives the same result, no duplicates) and
logged.
download_stats19.py : downloads the CSVs to
data/raw/<source>/<extraction_date>/ . Never modify these files.
fetch_weather.py : calls Open-Meteo and saves each JSON response untouched to
data/raw/weather/ .
Keep an ingestion log table ( ops.ingestion_log ) with: run id, source name,
extraction timestamp, file or API status (success / failed), row count, error message.
Wrap network calls with timeouts and retries (for example exponential backoff). On
failure, log it and continue or fail the task cleanly; never crash silently.
Read big CSVs with explicit dtypes, or in chunks, to keep memory in check.
6. Data layers and schema
Use separate Postgres schemas for each layer:
Star schema for the mart:
fact_accident: one row per accident, with keys to every dimension plus measures
(number of vehicles, number of casualties, severity key, weather measures).
dim_date: date, year, month, day, weekday, hour, is_weekend, is_rush_hour.
dim_road: road type, speed limit, junction detail, road surface condition.

8. Joining weather (the key design decision)
Do not call the API once per accident. There are 100k+ accidents per year, and you would
hit rate limits.
Instead:
1. Assign each accident to a grid cell by rounding coordinates (for example 0.25 degrees,
about 25 km). Store grid_cell_id  in dim_location .
2. Take the distinct cell centres (a few hundred for the UK).
3. For each cell centre, request the hourly historical weather for the whole date range in
one call (the API accepts a start and end date, and several locations per request).
Useful variables: temperature, precipitation or rain, wind speed, cloud cover, weather
code.
4. Store the result as staging.weather_hourly  (cell id, timestamp, variables).
5. Join: accident timestamp floored to the hour + accident's grid cell = weather row.
6. Report how many accidents had no weather match, and log them.
This is worth a paragraph in the report: it explains the trade-off between spatial accuracy
and API cost.
Rule Action
Severity not in {1,2,3} Reject
Speed limit outside plausible values Reject or set null (document which)
Coded values equal to -1 or 'data missing' Convert to null, keep the row
Orphan vehicle or casualty rows (no matching
accident)
Reject
Negative or absurd counts Reject

9. Aggregates and the model-ready table
Build these in mart :
Accidents by hour and by weekday (and the hour x weekday heatmap)
Accidents by road type and weather condition
Severity share by speed limit, light condition, road surface
Hotspots: counts per grid cell or local authority
Vehicle-type and casualty-age summaries
Build one wide mart.model_ready  table with one row per accident: the target
( severity ) plus features known at the time of the accident (hour, weekday, month, road
type, speed limit, junction, light, surface, weather values, urban/rural, location cell,
number of vehicles). Never edit it by hand; it is generated only by the pipeline.

PART 2: MLOps Extension
13. Problem framing and features
Task: multiclass classification of accident severity (Fatal / Serious / Slight). Fatal is rare
(typically around 1% of records), so the problem is heavily imbalanced.
Pick features from mart.model_ready :
Time: hour, weekday, month, is_weekend, is_rush_hour
Road: road type, speed limit, junction detail, surface, urban/rural
Environment: light condition, weather code, temperature, precipitation, wind
Location: grid cell id or coarse lat/long, local authority
Context: number of vehicles
Watch out for leakage. The number of casualties and any casualty-level fields are only
known after the accident, and severity is defined from casualty outcomes. Exclude them
from model inputs. The same applies to anything your API caller couldn't know at
prediction time.
Put all feature engineering in src/ml/features.py  so training and inference use identical
code.
14. Train, validation and test split
Use a chronological split: train on the earliest period, validate on the next, test on the
most recent. For example, with three years of data, train on years 1 and 2 (or the first 70%
by date), validate on the next block, and test on the last. This mimics real deployment and
avoids future data leaking into training. Document the exact date boundaries in the
report.

15. Class imbalance
Try at least one, and compare against the plain baseline:
Class weights ( class_weight='balanced'  for Random Forest, sample_weight  for
XGBoost/LightGBM)
Sampling (SMOTE or random undersampling), applied to the training set only, never
validation or test
Tune with the goal of recall on Fatal and Serious, since missing a severe accident is the
costly error.
16. Model development and evaluation
Baseline first (majority class or logistic regression), then Random Forest, XGBoost or
LightGBM.
Do light hyperparameter tuning on the validation set (grid or random search, a handful
of runs is fine).
Do not report accuracy alone; it looks great (about 80%+) just by predicting 'Slight'
every time.
Report on the test set: per-class recall, precision, F1, macro-F1, and a confusion
matrix. Highlight false negatives for the Fatal and Serious classes.
Add feature importances or SHAP for the interpretation section.
17. MLflow tracking and registry
For every training run, log:
Parameters: model type, hyperparameters, imbalance method, split dates, feature list
version
Metrics: macro-F1, recall per class, precision per class, validation and test scores
Artifacts: confusion matrix image, classification report, feature importance plot, the
fitted pipeline
Tags: data version or extraction date, git commit
Then:
1. Compare runs in the MLflow UI and pick a winner with a stated criterion (for example,
best macro-F1 subject to a minimum Fatal recall).

18. One inference pipeline
Package preprocessing and the model as a single scikit-learn Pipeline  (a
ColumnTransformer  for encoding and scaling, then the classifier), and log that one object
to MLflow. The API then receives raw field values and the pipeline does everything. This
prevents training and serving skew, which is a central MLOps point and will be asked
about in the viva.

23. Retraining criteria and model lifecycle
Define explicit, written triggers, for example:
PSI above 0.2 on key features or on the class distribution
Fatal recall or macro-F1 drops below a set threshold on newly labelled data
False-negative rate above an agreed limit
A new annual STATS19 release becomes available (scheduled retrain)
Sustained rise in input-quality failures
Then document the lifecycle: ingest new data (Part 1 DAG) -> rebuild model-ready table ->
retrain -> log to MLflow -> compare with the current production model -> promote only if
better -> deploy the new container -> monitor. A lifecycle diagram belongs in the report.
What How

releases), recompute macro-F1 and per-class recall
False-negative rate Share of actually Fatal or Serious accidents
predicted as Slight
Latency and failures p50/p95 latency, error rate, request counts

26. Common pitfalls
Calling the weather API per accident instead of per grid cell and hour.
Editing the final tables by hand, which the brief forbids; everything must come from
the pipeline.
Hardcoded passwords or API keys (use .env , and commit only .env.example ).
Judging the model on accuracy; use macro-F1 and per-class recall.
Random train/test split instead of chronological.
Resampling before splitting, which leaks information.
Using casualty counts as features (leakage).
Preprocessing outside the saved pipeline, so the API behaves differently from training.
Leaving documentation for the end; the report, data dictionary and diagrams carry
marks in both parts.
Committing large raw data files to git; add data/  to .gitignore  and document the
download step.
27. Definition of done
You're finished when someone can clone your repo, copy .env.example  to .env , run
docker compose up , trigger the Airflow DAG, open the Streamlit dashboard, submit a
prediction through the API, and see the drift and performance numbers, all by following
your README with no manual database edits.
